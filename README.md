# LifeCare Sample Tally V2.1 – simplified controls

Single barcode per participant, regardless of sample type. Existing turquoise UI retained. Netlify Functions + Netlify Blobs; no Supabase needed.

## Deploy / upgrade
1. Finish scanning and sync all phones in the existing version. Export each event before upgrade. Use a maintenance window: do not run the old app alongside V2. Keep a copy of the old site and its exports. Old legacy blobs are left intact but V2 writes only to `tally-v2`; reverting to V1 will NOT show new scans.
2. Extract this ZIP. Deploy the **whole project** via the existing Git-connected Netlify site or Netlify CLI (`npm install`, `npx netlify deploy --build --prod`). Do not drag only `public/index.html` into a static-site deployment; the function must be built. `netlify.toml` selects `public` and `netlify/functions`. The existing site must be used for migration from existing Blobs.
3. In Netlify environment variables (Functions scope), keep `ACCESS_CODE` as the administrator access code and add `STAFF_CODE` as a separate, long random scanner access code. Never reuse the same code. Redeploy after setting variables. Without STAFF_CODE only administrators can sign in. Use strong random codes; the local offline cache is encrypted using the sign-in code (PBKDF2/AES-GCM), but short codes are susceptible to guessing. Staff have read access to lists and scan access across the site; no individual user identity, per-event access controls, or formal compliance certification is provided.
4. Open Setup, sign in, choose the existing list. V2 migrates the legacy namelist, received records and scan exceptions on first opening that list. Legacy offline scans are quarantined for manual review, because they have no event generation identifier. Export and verify them before discarding. V2 prevents queued scans for an earlier replaced event being applied to a new event.
5. Test on a staging site with synthetic participants first. Do not use real patient records until your organization's security review, data-retention policy and live concurrency tests are complete.

## Features
- Scanner staff: scan, view counts, missing/received and export; admin: upload/edit namelists, register/replace/undo barcode, mark not attended/restore, archive/restore/clear, see amendment log. Device ID is a device label, not an authenticated individual identity.
- Excel (.xlsx first worksheet) and CSV input, Excel exports (CSV fallback). Name and Barcode columns; format barcode cells as Text before entering leading zeros. External pinned SheetJS and html5-qrcode libraries must be reachable on initial use. Without SheetJS, CSV remains available; without camera library use manual/hardware scanning.
- Pending scans persist before network submission. Waiting scans are not counted as confirmed. Rejected scans appear in Setup for export/review; discard only after verification. Offline mode requires initial successful sign-in and a cached list. The sign-out button is removed; the access code is retained in session storage. On shared devices, synchronize all scans before closing the tab. Avoid restoring authenticated tabs or sharing an active session. Clear browser site data only after confirming all waiting and blocked scans have been resolved. Browser storage can be cleared by the OS, quota limits, browser policies or private browsing; offline storage is not a substitute for backup.
- Archive makes an event read-only; select the archived event in the picker to review/export it. Restore to amend. Create a separate new event/PIC name for the next event instead of replacing an archived event. Clear is irreversible in V2; export first. Archived events retain participant details; establish a retention schedule.
- Activity log retains up to 3,000 changes per event; the UI displays the latest 100. Exception history capped at 10,000, recent 2,000 returned to UI. Scan operation replay IDs capped at 10,000.
- Polling: 12 seconds while visible, batches every 90 seconds, immediate refresh after scans. Shared state uses conditional writes and retries, not a transactional database. Appropriate for modest event volumes, but large/high-concurrency use requires load testing and potentially transactional database migration. Netlify Blobs docs: https://docs.netlify.com/build/data-and-storage/netlify-blobs/.
- PWA: open direct HTTPS URL in Android Chrome or iPhone Safari and install via the browser menu (no in-app install button). iOS standalone mode does not guarantee browser fullscreen API. Offline shell is cached after successful service worker installation; external scripts may need initial internet connection.
- My Apps iframe: the launcher must explicitly delegate camera and fullscreen to the sample tally origin. Example (substitute actual app URL):
  `<iframe src="https://YOUR-SAMPLE-TALLY.netlify.app/" allow="camera; fullscreen" allowfullscreen></iframe>`
  If the launcher has a restrictive Permissions-Policy or sandbox, its configuration must also permit camera/fullscreen, scripts and same-origin where required. iOS/browser privacy restrictions may still block camera/storage in a cross-origin iframe. Use the built-in Open scanner in browser fallback. This ZIP does not modify the separate My Apps launcher.

## Testing
`node --test tests/backend.test.mjs` uses a fake Netlify Blob store to check concurrency/retry flow, role enforcement, duplicate/replayed scans, barcode assignment, not-attended recovery, archive/restore, stale generation rejection and legacy migration. JavaScript syntax checks passed. Automated browser navigation was blocked by the execution environment; real browser, Excel CDN, mobile camera, offline PWA and production Netlify integration not verified.
